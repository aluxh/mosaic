# v0.1 — Deploy Spec

**Status:** Proposed
**Roadmap entry:** [`roadmap.md#v01-foundation`](roadmap.md)
**Builds on:** [`v0.1-foundation-spec.md`](v0.1-foundation-spec.md)

## Context

`v0.1-foundation` is code-complete: the slideshow runs locally, all 44
tests pass, `docker compose up --build` works on a dev box. What's left
to actually ship v0.1 is the deployment pipeline: getting the built
images onto a Synology NAS and running them under Dockhand
(<https://dockhand.pro/>) — a web UI that manages Docker stacks on the
NAS.

Building images on the NAS itself is slow (limited CPU, full `npm
install` for the Vite build). The plan is therefore: build on a fast
machine (locally or in GitHub Actions), push to GitHub Container
Registry (GHCR), and have Dockhand pull pre-built images.

The source repo is already public, so the images will be public too —
no GHCR auth needed in Dockhand for v0.1.

## Goals

1. A git tag `v0.1.0` triggers a CI build that pushes
   `ghcr.io/aluxh/mosaic-api:0.1.0` and `ghcr.io/aluxh/mosaic-web:0.1.0`
   (plus `:latest`) to GHCR as public images.
2. A single `docker-compose.prod.yml` file, pasted into Dockhand's
   stack editor on the NAS, runs both containers using the pulled
   images and the absolute volume path
   `/volume1/docker/mosaic/data`.
3. After deploy, the slideshow is reachable from the LAN at
   `http://<nas-ip>:8080/` and survives container/host restarts (data
   persists in the bind mount).
4. Local dev (`npm run dev`, `docker compose up --build`) keeps working
   unchanged — the prod compose file is additive, not a replacement.
5. A documented secrets policy lands now so v0.2 (which adds auth +
   HMAC keys) inherits the right defaults.

## Non-goals (v0.1 deploy)

- Multi-arch image builds — user confirmed amd64-only NAS.
- Smoke test that pulls and runs the pushed image in CI — useful but
  deferred; the `docker compose up` healthchecks already exist and
  the human verification step covers the deploy path.
- Auto-redeploy from Dockhand webhooks on new image push — manual
  "Re-pull & redeploy" in Dockhand is fine for v0.1.
- DNS / domain setup and DSM reverse-proxy HTTPS termination — these
  are environment-specific and live in README guidance, not code.
- Image vulnerability scanning, Dependabot, SBOM — v0.2+.
- Per-environment compose overlays (staging vs prod) — single instance
  for v0.1.

## User stories

1. **As the maintainer**, I tag a release locally with `git tag v0.1.0
   && git push --tags`, and within ~5 minutes both images are
   available at `ghcr.io/aluxh/mosaic-{api,web}:0.1.0`.
2. **As the maintainer**, on first deploy I SSH into the NAS, create
   `/volume1/docker/mosaic/data/{seeds,uploads}/{remembrance,celebration}/`,
   drop seed photos into `seeds/remembrance/`, open Dockhand in a
   browser, paste `docker-compose.prod.yml` into a new stack, hit
   Deploy, and the slideshow is live at `http://<nas-ip>:8080/`.
3. **As the maintainer**, to ship a new version I bump the tag, push,
   wait for GH Actions to finish, then in Dockhand click "Re-pull &
   redeploy" on the mosaic stack. SQLite data and uploaded photos
   persist across the redeploy.

## Repo changes

### 1. `docker-compose.yml` (existing — minimal edit)

Add an `image:` field alongside the existing `build:` so that local
`docker compose build` produces images tagged with their eventual
GHCR names. No behavior change for local dev.

```yaml
services:
  api:
    build:
      context: .
      dockerfile: Dockerfile.api
    image: ghcr.io/aluxh/mosaic-api:dev
    ...
  web:
    build:
      context: .
      dockerfile: Dockerfile.web
    image: ghcr.io/aluxh/mosaic-web:dev
    ...
```

### 2. `docker-compose.prod.yml` (new)

The file the maintainer pastes into Dockhand. No `build:`, pulls only,
absolute host path:

```yaml
services:
  api:
    image: ghcr.io/aluxh/mosaic-api:latest
    restart: unless-stopped
    environment:
      DATA_DIR: /data
      PORT: "3000"
      HOST: 0.0.0.0
    volumes:
      - /volume1/docker/mosaic/data:/data
    expose:
      - "3000"

  web:
    image: ghcr.io/aluxh/mosaic-web:latest
    restart: unless-stopped
    depends_on:
      - api
    ports:
      - "8080:80"
    volumes:
      - /volume1/docker/mosaic/data:/var/lib/mosaic-data:ro
```

Notes:
- Host port `8080` chosen to avoid conflict with anything on `:80`
  (DSM, Web Station, other stacks). DSM reverse proxy maps the
  public hostname → `localhost:8080` and handles HTTPS.
- `:latest` is the default tag for ease; the maintainer can pin to
  `:0.1.0` in Dockhand for a controlled redeploy.

### 3. `.github/workflows/release.yml` (new)

Triggers on git tags matching `v*.*.*`. Builds both images for
`linux/amd64` only and pushes to GHCR. Uses the built-in
`GITHUB_TOKEN` (no PAT needed for public images on the same org).

```yaml
name: Release

on:
  push:
    tags:
      - 'v*.*.*'

permissions:
  contents: read
  packages: write

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        include:
          - name: api
            dockerfile: Dockerfile.api
          - name: web
            dockerfile: Dockerfile.web
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/aluxh/mosaic-${{ matrix.name }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=raw,value=latest

      - uses: docker/build-push-action@v5
        with:
          context: .
          file: ${{ matrix.dockerfile }}
          platforms: linux/amd64
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

After the first successful push, the maintainer goes to
<https://github.com/users/aluxh/packages> and sets both packages to
**Public** + links them to the `mosaic` repo.

## Secrets policy (forward-looking, lands now)

A short section in `README.md` and a comment in
`docker-compose.prod.yml` stating:

> Secrets (admin password, HMAC signing keys, JWT secrets — none in
> v0.1, several in v0.2) MUST be provided via the `environment:`
> block of the prod compose file on the NAS. Never `COPY` a `.env`
> file into a Dockerfile, never commit `.env` to the repo, never
> hardcode secrets in source. `.dockerignore` already excludes
> `.env*`; do not remove that line.

No code changes for v0.1 since there are no secrets yet — this is a
written commitment so v0.2 inherits the right default.

## Tests

This spec produces no new unit tests. The verification surface is:
- **CI (automated):** the existing `ci.yml` keeps running `npm test`
  on push/PR. The new `release.yml` only runs on tag push; it is its
  own test (success = both images built and pushed).
- **Manual:** the verification checklist below is the acceptance test
  for the deploy story.

Out of scope: a post-build smoke job that pulls the freshly-pushed
image and hits `/health`. Worth adding when we add a second image
target or migrate to multi-arch.

## Acceptance criteria

The deploy story is done when:

1. `docker-compose.yml` has `image:` fields on both services and
   `docker compose build` still works locally.
2. `docker-compose.prod.yml` exists and contains only `image:`
   references (no `build:`) plus the absolute Synology volume path.
3. `.github/workflows/release.yml` exists, is triggered by tag push,
   and produces both `mosaic-api` and `mosaic-web` packages under
   `github.com/users/aluxh/packages`.
4. Both packages are marked Public and linked to the `mosaic` repo.
5. README has a "Deploying to Synology" section and a "Secrets
   policy" subsection.
6. On the NAS, pasting `docker-compose.prod.yml` into Dockhand and
   hitting Deploy results in a reachable slideshow at
   `http://<nas-ip>:8080/`.
7. Restarting the host or the containers preserves SQLite rows and
   uploaded files.
8. A redeploy (Dockhand "Re-pull & redeploy") with a newer image tag
   picks up the new code without data loss.

## Verification (manual)

Repo side:
1. Apply repo changes (compose edits, new prod compose, new workflow,
   README updates).
2. `docker compose build` locally → both images build with the new
   `image:` tags.
3. `git tag v0.1.0 && git push --tags` → GH Actions Release workflow
   runs to green.
4. Confirm both packages exist at
   <https://github.com/users/aluxh/packages>; set both to Public if
   not auto-public.

NAS side:
5. SSH in, run:
   ```
   sudo mkdir -p /volume1/docker/mosaic/data/seeds/{remembrance,celebration}
   sudo mkdir -p /volume1/docker/mosaic/data/uploads/{remembrance,celebration}
   ```
6. Copy 3-5 test JPGs into
   `/volume1/docker/mosaic/data/seeds/remembrance/`.
7. Open Dockhand → new Stack → name `mosaic` → paste
   `docker-compose.prod.yml` → Deploy.
8. Watch Dockhand logs: both containers reach healthy state.
9. Open `http://<nas-ip>:8080/` on a phone and on the TV browser →
   slideshow plays, shows seeded photos.
10. Hit the contribute sheet, upload a photo, confirm it appears
    within ~10s.
11. From Dockhand, stop and restart the stack → uploaded photo and
    SQLite data persist.

## Open questions

- **Image tag policy.** Default to `:latest` in the prod compose for
  one-click redeploys, or default to `:0.1.0` (pinned) and require an
  explicit edit per release? Spec assumes `:latest` for v0.1; can
  revisit once we have a real release cadence.
- **Dockhand auto-deploy webhook.** Dockhand supports webhook
  triggers for redeploy on image push. Deferred — adds another moving
  part and v0.1 is single-maintainer single-event.
- **GHCR rate limits.** Public packages have no documented pull-rate
  limit on GHCR today, but this could change. Not a v0.1 concern.
